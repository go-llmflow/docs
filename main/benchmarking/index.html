Benchmarking

Benchmarking

The bench repository holds two small command-line tools, in pure Go, for measuring LLM gateways such as the gateway: gwbench measures the latency a gateway adds, and fakevllm is the upstream it is measured against. Repository →

This page is written from the repository’s README at v0.2.0; v0.3.0 adds the fakeupstream package (the fake vLLM as a Go package, for tests that embed it with httptest) and the e2e/oidc suite, described on the Identity page. No command or flag of gwbench or fakevllm changed. Since v0.1.0, gwbench has a --direct-model flag (the model name the upstream serves, sent on the direct path), fakevllm is a cobra command line, and an e2e/ suite checks the gateway against a real vLLM (see Verified against a real vLLM).

go install github.com/go-llmflow/bench/cmd/gwbench@latest
go install github.com/go-llmflow/bench/cmd/fakevllm@latest

What is measured

The question is “how much latency does a gateway add?”, not “how fast is the model”. The upstream must therefore answer as fast as possible: that is fakevllm, which replies instantly. The number reported is a difference between two paths to the same upstream, not a latency.

direct calls the upstream itself. Every other target (--litellm, --llmflow, or --target NAME|URL|KEYFILE, repeatable) is a gateway forwarding to that same upstream.

The method

Interleaving

Each round sends one request to every target, one at a time, in a fresh random order (seeded with --seed). Drift of the machine (thermal state, a background job, the cache) then spreads evenly over all targets instead of penalising whichever runs last. The first --warmup rounds are discarded.

Pairing

A gateway’s overhead in round r is its latency minus the direct latency of the same round. Percentiles are taken over these paired differences, which cancels what both paths share: the client, the loopback and the upstream.

Load gating

Ratios measured on a busy machine are meaningless. A run starts only when the 1-minute load average is at most --max-load (default 4). With --wait, the tool waits for the load to fall; without it, it refuses at once. A run whose load ends above the limit is discarded, not averaged. --runs kept runs are collected, and their rounds stay paired when they are merged.

The load is read from /proc/loadavg on Linux and from sysctl vm.loadavg on macOS. Elsewhere the tool cannot read it and refuses to measure.

The control

TestPlantedOverheadIsMeasured puts a proxy that sleeps a known 3 ms and a transparent proxy in front of a test upstream. The instrument must report about 3 ms for the first and about 0 for the second, and separate the two. If it could not see a planted delay, its verdict on real gateways would mean nothing.

Requests

Requests are POST chat completions with max_tokens: 1 and one user message: ping, or the content of --prompt-file, sent as a JSON string. An HTTP status other than 200 aborts the run: an error is never timed as a success.

Keys

Keys are read from files, never from the command line or the environment. A KEYFILE may be empty for an open endpoint. gwbench llmflow-key creates an llmflow virtual key through the admin API (--master-key-file) and writes it to a file of mode 0600. Keep key files outside the repository.

An example 

fakevllm --addr 127.0.0.1:18000 --out /tmp/requests.jsonl &
llmflow-gateway serve --config llmflow.hcl &      # forwards to 127.0.0.1:18000
gwbench llmflow-key --admin http://127.0.0.1:18080 --master-key-file ~/keys/master --out ~/keys/llmflow
gwbench run --direct http://127.0.0.1:18000/v1/chat/completions \
  --target 'v0.8.0|http://127.0.0.1:18080/v1/chat/completions|'"$HOME"'/keys/llmflow' \
  --rounds 2000 --warmup 200 --runs 8 --wait 2h --max-load 4

Dated results

Overhead is the paired difference against a direct call to the same upstream. Each result is tied to its date and protocol; none is a promise for another machine, another load or another request.

Common to both dates. Machine: Apple M4 Max (Mac16,5), 16 cores, 128 GiB RAM, macOS 27.0.1. Each gateway ran with GOMAXPROCS=1; LiteLLM 1.106.2 ran as one process. Upstream: fakevllm on loopback, answering instantly. Client: gwbench, requests one at a time, target order shuffled every round. Each kept run is 2,000 rounds after a warm-up of 200, and the 1-minute load was at most 4 at its start and at its end.

Verified against a real vLLM (2026-10-26)

The gateway’s design rests on vLLM behaviours read in vLLM’s documentation and source. The e2e/ suite of bench checks them live: it starts llmflow-gateway with freshly generated keys, creates a virtual key per team, and drives it in front of a running vLLM. Without BENCH_VLLM_URL every test skips, so CI runs none of them.

VariableMeaning
BENCH_VLLM_URLthe chat vLLM (required)
BENCH_VLLM_MODELits model name (default: the first of /v1/models)
BENCH_GATEWAY_BINthe llmflow-gateway binary (default: from PATH)
BENCH_VLLM_MAX_NUM_SEQSthe server’s --max-num-seqs (the scenarios need 2)
BENCH_VLLM_KV_SHORTAGE=1vLLM runs with a tiny KV cache: enables the preemption checks
BENCH_VLLM_EMBED_URL, BENCH_VLLM_RERANK_URLoptional embedding and score-model servers

Setup. vLLM 0.32.1rc1 (nightly CPU image) in arm64 Docker on an Apple M4 Max; models Qwen2.5-0.5B-Instruct (bfloat16), bge-small-en-v1.5 and bge-reranker-base; gateway v0.8.0. The released v0.32.0 arm64 image failed every CPU generation (compute_slot_mapping), which is why the nightly was used; that failure concerns the CPU build only. The gateway configuration is organisation A (two teams, share 0.5) and B (one team, share 0.25) on a pool of capacity 2, so A reserves one slot and every request of B borrows; cache_isolation = "org".

Every ordering check has a control straight to vLLM that must come out the other way, and the cache checks read vLLM’s own counters, never timing.

Not covered: audio transcription (no Whisper model run on CPU) and throughput.

fakevllm 

fakevllm --addr 127.0.0.1:18000 --out requests.jsonl --model fake --reply "ok"

Flags: --addr, --out, --model, --reply, --delay, --token-delay, --max-body.

RouteAnswer
GET /v1/modelsone model, named by --model
POST /v1/messagesan Anthropic message; with "stream": true, the event sequence message_start, content_block_start, content_block_delta…, content_block_stop, message_delta (with usage.output_tokens), message_stop
any other POSTan OpenAI chat.completion; with "stream": true, chat.completion.chunk events (role, one chunk per word of --reply, finish), the usage chunk with empty choices when stream_options.include_usage is set, then data: [DONE]

Usage is predictable: one prompt token per whitespace-separated word of the request’s message and system strings, and one completion token per word of --reply. --delay and --token-delay slow the answer and the stream.

Every request is appended to --out (mode 0600) as one JSON line, {"method","path","headers","body"}; a body that is not JSON is recorded as a string. The recording holds the headers as received, Authorization included. That is by design, since it is a witness of what a gateway forwarded. Use test keys only. If the record cannot be written, the request gets a 500, so a test never reads a silent gap as “nothing was forwarded”. Bodies are capped by --max-body (1 MiB; larger ones get a 413).

Workload profiles

Workload profiles

An administrator, often in finance or HR rather than IT, gives each person a workload profile in working days per week instead of a money budget: a quarter day, half a day, one day … seven days a week. The gateway turns the profile into hard budgets, so a profile is never exceeded (with the edges listed there). Since v0.18.0. This page is written from the repository’s README at that tag; it was not run on a production cluster.

The unit: a workday

A workday is what one person working with the assistant for a full day consumes, in each cost unit: GPU-hours for the local pools and a currency for each external provider. It is measured, not guessed:

  • /ui/profiles/calibrate (or GET /admin/profiles/calibrate?weeks=4) shows the distribution of the cost of every active person-day (a person with any cost that day) over the last weeks, and proposes its 75th percentile.
  • A proxy admin accepts a value (POST /admin/profiles/calibrate {"unit": "USD", "amount": 13}, audited), and every profile follows at once.
  • For reference, Anthropic reports about $13 per developer per active day for Claude Code across enterprise deployments (costs), but your own measurement is what counts.
  • An accepted calibration takes precedence over a workday block in the configuration, which only gives a starting value.
  • A priced request in a unit without a workday is refused (503) for a person under a profile: nothing could hold its cost against the profile.

What a profile becomes

For a person with a profile of d days, in every unit that has a workday:

BudgetPeriodLimit
profile_weekthe ISO 8601 week, reset Monday 00:00 UTCd x workday
profile_sessiona rolling window, session_window (5 h by default)session_share x workday
profile_overflowthe calendar month, only when overflow is allowed for the personoverflow_cap x workday

The session window stops one person from burning the week in one sitting, as the five-hour session limit of Anthropic’s plans does (Max plan, Team plan). The profiles do not borrow those plans’ names: their ratios do not match a day scale. The labels default to the day count ("2 days / week") and can be changed.

Overflow is the analogue of Anthropic’s capped usage credits (manage usage credits). When the week or the session refuses a request and an administrator allowed overflow for that person, the request is admitted on the profile’s monthly overflow_cap instead. It is marked overflow in its record, counts for the overflow budget only, and still counts for every other budget of its scope (team, organisation, project). An organisation-wide cap is an ordinary org budget. Without overflow, the request is refused.

Refusals are 429 insufficient_quota with X-Llmflow-Budget-Reset. The message is in workdays and names only the caller’s own allowance, for example:

weekly allowance of 2 days used; resets Monday 2 Nov 00:00 UTC
session allowance of 0.5 day per 5h: 0.1 day left, and this request may cost up to 0.2 day (send a smaller max_tokens, or wait: room again from Wednesday 28 Oct 15:35 UTC)

For the session window the header gives when enough has left the window for the request, not the end of a period.

The rolling window ("period": "rolling:5h", a general budget period, 5 minutes to 168 hours in whole 5 minutes, no soft_limit) keeps its spend in 5-minute buckets, so its spent counts at most 5 minutes more than the window, never less; a request counts in the bucket of its end. Since v0.18.1 the buckets are kept for the longest window that can apply (7 days, at most 2016 buckets per budget), so widening session_window no longer forgets spend (defect #98 of v0.18.0, see Security). Replica clocks must be in sync, as for calendar periods.

Who assigns

  • A proxy admin assigns anyone.
  • An org_admin assigns a person all of whose team bindings are in their organisation (see the v0.18.1 rule below).
  • A team_admin assigns a person all of whose bindings are in teams they administer.
  • A person with a binding in another organisation, a proxy role, or no binding at all (a JWT’s user) is the proxy admins’ only: a profile limits the person everywhere, so one organisation does not decide it for another.
  • People read their own profile; administrators and viewers read the people of their scope.

Since v0.18.1, membership is the team bindings (which SSO and SCIM also create). An organisation-level binding (viewer, org_admin) is authority, not membership: it gives no access to the person, whoever granted it. So an org_admin no longer assigns another org_admin who is in no team: ask a proxy admin. The same rule applies to the user budgets API. (The README’s “Who assigns” paragraph at v0.18.1 still has the older wording; this page follows its “Security fixes in v0.18.1” section.) A further case, #104 (a team-role grant to a user with no binding), is fixed in v0.18.2: the first grant to such a user needs a proxy admin, and a team binding an org admin granted does not make the person theirs; see Security.

Every assignment is stored with its history (who, when, which profile) and audited.

Configuration 

workday {               # optional starting values; a calibration accepted in the UI wins
  gpu_hours = 0.8
  USD       = 13        # one attribute per unit, as the models spell it
}
profile "q" {           # id: [a-z0-9_-]{1,32}; at most 64 profiles
  days          = 0.25  # 0..7 days a week
  session_share = 0.25  # (0, 1] workday per session window
}
profile "2d" {
  label         = "2 days / week"  # default: the day count; at most 64 printable bytes
  days          = 2
  session_share = 0.5
  overflow_cap  = 2     # optional, 0..217 workdays a month beyond the profile
}
default_profile = "q"   # optional: everyone without an assignment
session_window  = "5h"  # 5m..24h in whole 5 minutes

This block, with budgets, models and organisations around it, passes llmflow-gateway check-config v0.22.0. HCL allows one attribute only in a block written on one line (profile "q" { days = 0.25 }): write one attribute per line. A person with default_profile gets their budgets at their first request, which waits up to 3 s for them to arm, once. The budgets API neither lists nor changes the profile budgets (PUT /admin/budgets with a profile_* kind answers 404).

Admin API 

PUT    /admin/users/{user}/profile   {"profile": "2d", "overflow": false}
DELETE /admin/users/{user}/profile   # back to default_profile, or none
GET    /admin/users/{user}/profile   # the person's week and session, in days, and the history
GET    /admin/profiles               # the profiles, the default, the workday in force per unit and its source
GET    /admin/profiles/people        # ?org= or ?team=: everyone the principal may read
GET    /admin/profiles/capacity      # see below
GET    /admin/profiles/calibrate     # ?weeks=1..26 (proxy roles)
POST   /admin/profiles/calibrate     # {"unit", "amount"} (proxy admins)

The admin pages

  • /ui/profiles shows each person’s week as a bar in days (“1.3 / 2 days”) with when it resets, their session and their overflow, and offers the assignment form to those who may assign.
  • /ui/profiles/capacity is the check a manager needs: it compares the days assigned each week to an organisation’s people with what its share of the pools serves (share x C x the measured cost per request-slot-hour over the last 7 days of records x 168 h, in workdays), and shows the oversubscription ratio as a seat count would (“assigned 140 days a week for a capacity of about 90, x1.6”). Oversubscription is normal, since people do not all work at the same time and fair share arbitrates when they do. A pool without measured load says “not measured”; an external provider has no capacity, since it is billed per request.
  • /ui/profiles/calibrate is the calibration above.

Reports

Finance reports gain a profile dimension (group_by=profile, the reports page, and the CSV, XLSX and PDF exports): the profile in force when each request was admitted, so a change of profile never rewrites history.

Upgrading from v0.17 to v0.18

  • Start-up adds the tables llmflow_budget_buckets, llmflow_profile_assignments and llmflow_workdays, and the profile and overflow columns of llmflow_usage. Existing records have no profile and are not overflow. Nothing changes without profile blocks.
  • With profiles, calibrate a workday for every unit a person under a profile uses before setting default_profile; until then their priced requests in that unit are refused.
  • Upgrade every replica before assigning profiles. A v0.17 replica does not know the profile kinds: it admits without holding on them, and the arming of each new profile budget covers its requests only until their records are stored.
  • Fixed on the way: a budget deleted and created again now re-reads its period’s spend from the records.

Soft quotas: warnings before a window runs out (since v0.19.0)

The hard budgets never let a window be exceeded; soft quotas tell people before it runs out, the way Anthropic does for its five-hour session and weekly limits. By default a person is warned once past 75 % and again past 95 % of a window (Anthropic’s values: see usage warnings in Claude Code). The windows are the profile’s session and week, and a money budget with a user scope.

What is not done. Claude Code’s own warnings read anthropic-ratelimit-unified-* response headers, whose exact format is documented only in a Claude apps gateway’s own protocol reference, which is not public. The gateway does not emit them and guesses nothing. The warnings reach people through the channels below, which the gateway controls.

ChannelWhat it is
response headerson every successful response, for the caller’s own windows only: X-Llmflow-Usage-Session, -Session-Reset (RFC 3339), -Week, -Week-Reset, and past a threshold X-Llmflow-Usage-Warning (French with Accept-Language: fr)
GET /v1/me/usagewith the caller’s own key or token, rate limited (60 a minute per key), no-store: windows, percentages, reset times, the profile and the thresholds in force
llmflow-statusa small program for Claude Code’s statusLine, below
notificationsat each threshold, once per window: a webhook (with an Idempotency-Key) and/or mail from the alerts block, to the person when their user name is an address and, with notify = ["user", "team_admin"], to the administrators of their teams; at least once, shared by the replicas
admin UI/ui/softquotas: who is above a threshold in the current windows, and the thresholds of each level

The hard limit now speaks as Anthropic’s does: 429 with “You’ve hit your session allowance” (or weekly) and its reset time, retry-after in integer seconds, the existing X-Llmflow-Budget-Reset, and x-should-retry: false; Claude Code stops retrying above 60 seconds and shows the message at once.

Thresholds, from the most general level to the most specific, which wins:

soft_quotas {
  warn_at  = [75, 95]          # the gateway; Anthropic's values when omitted
  language = "fr"              # of warnings when a request names none (en by default)
  timezone = "Europe/Paris"    # the zone reset times are spelled in (UTC by default)
  notify   = ["user", "team_admin"]   # who is mailed (user by default)
}
org "etabA" {
  share = 0.8125
  soft_quotas {
    warn_at = [80, 95]         # one organisation
  }
}
profile "2d" {
  days = 2
  session_share = 0.5
  soft_quotas {
    warn_at = [50, 75, 95]     # one profile
  }
}

This block, in a complete file, passes llmflow-gateway check-config v0.19.0; with warn_at = [95, 75] it answers “want a strictly increasing list”. A user budget takes warn_at from the budgets API (PUT /admin/budgets, "warn_at": [60], user scope only). Resolution: gateway, organisation, profile, budget (the budget wins). One to five thresholds, integers from 1 to 99, strictly increasing; [] turns warnings off for that level. An organisation administrator sets their organisation’s thresholds in the UI (PUT /admin/soft-quotas/orgs/{name}); the gateway default and the profiles’ are the proxy administrators’ (PUT /admin/soft-quotas/gateway and /profiles/{name}); DELETE goes back to the configured value. Every change is audited and the other replicas apply it within 15 s.

Once per window instance, across replicas. A threshold fires once per window instance, decided by one row per person, window and threshold in PostgreSQL. The session is a rolling window with no start, so a fired threshold is armed again only when usage falls below it by a hysteresis (5 points, or half the threshold when smaller: 75 re-arms below 70). When several thresholds are crossed at once only the highest is notified. The repository’s property test (three replicas, random kills) checks exactly one firing per week and per episode, with a planted control that fires more than once; this page did not run it.

Claude Code’s status line. Install llmflow-status:

go install github.com/go-llmflow/gateway/cmd/llmflow-status@latest

and add to ~/.claude/settings.json (status line):

{
  "statusLine": {
    "type": "command",
    "command": "llmflow-status",
    "refreshInterval": 30
  }
}

refreshInterval re-runs the command every N seconds, so the usage and reset time stay current while the session is idle. The program reads the status line’s JSON on stdin, calls /v1/me/usage at ANTHROPIC_BASE_URL with ANTHROPIC_AUTH_TOKEN (else ANTHROPIC_API_KEY) and prints, for example, session 85% · 15:45 │ week 40% · Mon 00:00, green below the first threshold, yellow past some, red past the last (NO_COLOR or --no-color for none). It caches the answer for 30 s in the user cache directory (no secret in it). On any error or timeout (2 s) it prints nothing and exits 0, and it never prints the credential; it refuses to send it over plain http except to this machine, and never follows a redirect. If an apiKeyHelper supplies the credential and neither variable is set in the status line’s environment, pass --token-file: the status line documentation does not say which variables the command inherits. llmflow-status --help (v0.19.0) lists --url, --token-file, --ttl, --timeout, --lang, --allow-http, --no-color and --verbose. This page installed it; it did not run it against a gateway.

Continue and any client without a status line show no native warning: read the X-Llmflow-Usage-* headers from your own tooling, or GET /v1/me/usage; the notifications reach people regardless of the client.

Upgrading. See Decision reports. The refusal text of a profile changed (Anthropic’s wording, with the numbers in days in parentheses). Not measured: the admission benchmark was not run for this change (the machine was loaded); the request path adds one profile lookup and a handful of in-memory reads per request.

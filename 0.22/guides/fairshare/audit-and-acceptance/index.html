Audit anchor. The Go gateway (audit log since v0.5.0) keeps a hash-chained audit log of every administrative change, with signed checkpoints. A log in the database that the operator can edit is only partly trustworthy: deploy the audit anchor on the same S3 or Ceph storage the cluster already has, in a bucket created with Object Lock, so that exported checkpoints cannot be deleted or rewritten, and check the log with llmflow-gateway audit verify --anchor export and a public key kept outside the operators’ reach. Without an anchor, truncation and rollback go undetected. The Audit and logging page states what remains open.

Guardrails (gateway v0.6.0). Prompts and completions can be checked before and after vLLM, on this cluster, without sending them anywhere: hide_secrets masks tokens and URL credentials (using gitsafe’s redact), pii masks or blocks personal data (e-mail, phone, IBAN, French NIR, cards, IP addresses) with go-llmflow/pii, and llama_guard and prompt_guard classify with a Llama Guard or Prompt Guard model served locally by vLLM on the cluster, as a model of class guard that clients cannot call. The classifiers see the already-masked text. A guardrail that errs or times out refuses (503) by default. The generic HTTP adapter is off by default: it exists only when written, and then only with allow_external = true, because it sends prompts and completions out of the site. This block passes check-config v0.22.2:

guardrail "secrets" {
  type = "hide_secrets"
  orgs = ["instA", "instB"]
}
guardrail "pii" {
  type    = "pii"
  teams   = ["b-lab"]
  action  = "mask"
  actions = { iban = "block", nir = "block", phone = "log" }
}
guardrail "safety" {
  type     = "llama_guard"
  model    = "llama-guard"
  teams    = ["b-lab"]
  action   = "block"
  timeout  = "2s"
  on_error = "block"
}

model "llama-guard" {
  upstream_model = "meta-llama/Llama-Guard-3-8B"
  pool           = "guard"
  class          = "guard"
  key_file       = "/etc/llmflow/vllm.key"
  upstream "g0" { base_url = "http://gpu09:8000" }
}

(Alongside the organisations, teams, the pool "guard" and the other models.)

Chaos to play during acceptance. Kill a vLLM instance under sustained traffic (the routing must fail over); cut Redis (the fail-closed mode must answer 503, not let requests through); preempt a borrowed job in the middle of writing a checkpoint (the resume must read the last complete checkpoint); restart slurmdbd during a mass submission.

Acceptance tests: prove the guarantee holds

Every guarantee is proven by a test that could fail:

  1. B’s guarantee. A fills the 32 GPUs (13 in instA, 19 in borrow). B submits 3 GPUs in instB. Measure the start delay: it must stay under 36 minutes, and under 6 minutes if the borrowed jobs are older than 30 minutes.
  2. Negative control. The same scenario with the borrow QOS without Preempt: B must wait. If B starts anyway, test 1 was not measuring preemption.
  3. Cap. B submits 8 GPUs in instB: immediate rejection (DenyOnLimit).
  4. Fair-share. After a week in which B borrows heavily, sshare -l must show LF_B < 1, and A’s borrow jobs must go ahead of B’s (sprio).
  5. Billing. A job of 1 GPU and 64 cores must be billed 4: the billing= field of AllocTRES in sacct.
  6. Inference. Saturate the model with a key of A; check that a key of B still gets about 18.75 % of the throughput (with the Enterprise reservation, or the relay) or its static limit.
  7. vLLM priority. During saturation, a request of the large-model group (priority 0) must have a time to first token markedly lower than a request of large-model-batch (priority 10).
  8. Inviolable priority. Send to large-model-batch a request with extra_body: {"priority": 0} and a header X-Vllm-Priority: 0. It must stay processed at priority 10. Control: the same request sent directly to vLLM goes ahead.
  9. B’s window. One hour before instB_weekly opens, submit in borrow a 3 h job and a 30 min job. Only the second must start on the reserved server. At opening, an 8-GPU job of B must start immediately.

Performance. Compare throughput (tokens/s) and latency (time to first token, p50/p99) of vLLM behind the gateway with those of vLLM direct, at equal load. The gateway’s overhead must stay negligible next to generation; if it does not, increase the number of gateway workers before touching vLLM.

Governance

  • Agreement between institutions: shares (26/6), guaranteed delay (36 min), size of the inference pool, half-life (14 days), the quarterly compensation rule, and the possible reservation of a whole server for B.
  • Quarterly technical committee: real consumption against share, median wait times per institution and per QOS, preemption rate, inference saturation.
  • Change of shares (the purchase of a 5th server, say): change the Fairshare and GrpTRES values. No redeployment is needed.

Benchmarking

Benchmarking

The bench repository holds two small command-line tools, in pure Go, for measuring LLM gateways such as the gateway: gwbench measures the latency a gateway adds, and fakevllm is the upstream it is measured against. Repository →

This page is written from the repository’s README at v0.7.0 (and v0.2.0 for the parts that did not change). v0.7.0 adds a live test of the gateway’s hard budgets (see Hard budgets). v0.6.0 adds a live test of the HA mutual TLS (see HA mutual TLS). v0.5.0 adds a fake slurmrestd and the Slurm end-to-end test (see Slurm discovery). v0.4.0 teaches fakevllm to mimic Anthropic’s API and adds the e2e/anthropic suite (see fakevllm and Anthropic upstream); v0.3.0 added the fakeupstream package (the fake vLLM as a Go package, for tests that embed it with httptest) and the e2e/oidc suite, described on the Identity page. No command or flag of gwbench or fakevllm changed. Since v0.1.0, gwbench has a --direct-model flag (the model name the upstream serves, sent on the direct path), fakevllm is a cobra command line, and an e2e/ suite checks the gateway against a real vLLM (see Verified against a real vLLM).

go install github.com/go-llmflow/bench/cmd/gwbench@latest
go install github.com/go-llmflow/bench/cmd/fakevllm@latest

What is measured

The question is “how much latency does a gateway add?”, not “how fast is the model”. The upstream must therefore answer as fast as possible: that is fakevllm, which replies instantly. The number reported is a difference between two paths to the same upstream, not a latency.

direct calls the upstream itself. Every other target (--litellm, --llmflow, or --target NAME|URL|KEYFILE, repeatable) is a gateway forwarding to that same upstream.

The method

Interleaving

Each round sends one request to every target, one at a time, in a fresh random order (seeded with --seed). Drift of the machine (thermal state, a background job, the cache) then spreads evenly over all targets instead of penalising whichever runs last. The first --warmup rounds are discarded.

Pairing

A gateway’s overhead in round r is its latency minus the direct latency of the same round. Percentiles are taken over these paired differences, which cancels what both paths share: the client, the loopback and the upstream.

Load gating

Ratios measured on a busy machine are meaningless. A run starts only when the 1-minute load average is at most --max-load (default 4). With --wait, the tool waits for the load to fall; without it, it refuses at once. A run whose load ends above the limit is discarded, not averaged. --runs kept runs are collected, and their rounds stay paired when they are merged.

The load is read from /proc/loadavg on Linux and from sysctl vm.loadavg on macOS. Elsewhere the tool cannot read it and refuses to measure.

The control

TestPlantedOverheadIsMeasured puts a proxy that sleeps a known 3 ms and a transparent proxy in front of a test upstream. The instrument must report about 3 ms for the first and about 0 for the second, and separate the two. If it could not see a planted delay, its verdict on real gateways would mean nothing.

Requests

Requests are POST chat completions with max_tokens: 1 and one user message: ping, or the content of --prompt-file, sent as a JSON string. An HTTP status other than 200 aborts the run: an error is never timed as a success.

Keys

Keys are read from files, never from the command line or the environment. A KEYFILE may be empty for an open endpoint. gwbench llmflow-key creates an llmflow virtual key through the admin API (--master-key-file) and writes it to a file of mode 0600. Keep key files outside the repository.

An example 

fakevllm --addr 127.0.0.1:18000 --out /tmp/requests.jsonl &
llmflow-gateway serve --config llmflow.hcl &      # forwards to 127.0.0.1:18000
gwbench llmflow-key --admin http://127.0.0.1:18080 --master-key-file ~/keys/master --out ~/keys/llmflow
gwbench run --direct http://127.0.0.1:18000/v1/chat/completions \
  --target 'v0.8.0|http://127.0.0.1:18080/v1/chat/completions|'"$HOME"'/keys/llmflow' \
  --rounds 2000 --warmup 200 --runs 8 --wait 2h --max-load 4

Dated results

Overhead is the paired difference against a direct call to the same upstream. Each result is tied to its date and protocol; none is a promise for another machine, another load or another request.

Common to both dates. Machine: Apple M4 Max (Mac16,5), 16 cores, 128 GiB RAM, macOS 27.0.1. Each gateway ran with GOMAXPROCS=1; LiteLLM 1.106.2 ran as one process. Upstream: fakevllm on loopback, answering instantly. Client: gwbench, requests one at a time, target order shuffled every round. Each kept run is 2,000 rounds after a warm-up of 200, and the 1-minute load was at most 4 at its start and at its end.

Verified against a real vLLM (2026-10-26)

The gateway’s design rests on vLLM behaviours read in vLLM’s documentation and source. The e2e/ suite of bench checks them live: it starts llmflow-gateway with freshly generated keys, creates a virtual key per team, and drives it in front of a running vLLM. Without BENCH_VLLM_URL every test skips, so CI runs none of them.

VariableMeaning
BENCH_VLLM_URLthe chat vLLM (required)
BENCH_VLLM_MODELits model name (default: the first of /v1/models)
BENCH_GATEWAY_BINthe llmflow-gateway binary (default: from PATH)
BENCH_VLLM_MAX_NUM_SEQSthe server’s --max-num-seqs (the scenarios need 2)
BENCH_VLLM_KV_SHORTAGE=1vLLM runs with a tiny KV cache: enables the preemption checks
BENCH_VLLM_EMBED_URL, BENCH_VLLM_RERANK_URLoptional embedding and score-model servers

Setup. vLLM 0.32.1rc1 (nightly CPU image) in arm64 Docker on an Apple M4 Max; models Qwen2.5-0.5B-Instruct (bfloat16), bge-small-en-v1.5 and bge-reranker-base; gateway v0.8.0. The released v0.32.0 arm64 image failed every CPU generation (compute_slot_mapping), which is why the nightly was used; that failure concerns the CPU build only. The gateway configuration is organisation A (two teams, share 0.5) and B (one team, share 0.25) on a pool of capacity 2, so A reserves one slot and every request of B borrows; cache_isolation = "org".

Every ordering check has a control straight to vLLM that must come out the other way, and the cache checks read vLLM’s own counters, never timing.

The vLLM-beyond---max-num-seqs row is why saturation needs its own rule: vLLM queues instead of refusing, so a fallback on an outage never sees a queue. The last row is the check of that rule. TestFallbackOnSaturation needs BENCH_VLLM_MAX_NUM_SEQS=4 (a vLLM started with --max-num-seqs 4) and a gateway of v0.11.0 or later; it skips otherwise.

Not covered: audio transcription (no Whisper model run on CPU) and throughput.

Anthropic upstream

e2e/anthropic (bench v0.4.0) checks the gateway’s Anthropic upstream against fakevllm playing Anthropic. It needs BENCH_GATEWAY_BIN set to a gateway of v0.12.0 or later. It checks that:

  • the request leaves with the organisation’s key, not the client’s credential, and without the OAuth beta;
  • the PII is masked, and cache_salt and priority are gone, before egress;
  • streams work, and /v1/chat/completions is refused;
  • the spend report, in USD, equals the price list applied to the usage the provider reported;
  • a 429 with retry-after makes the gateway answer 429 itself, for that organisation only.

Result: on 2026-10-26 the fake-API suite passes against gateway v0.12.0. It proves the gateway’s behaviour against a fake; it says nothing about Anthropic’s real API. A second test, TestGatewayInFrontOfRealAnthropic, runs only when BENCH_ANTHROPIC_KEY_FILE names a file holding a key (the model is BENCH_ANTHROPIC_MODEL, default claude-haiku-5-5). It was not run for v0.4.0, since no key was available.

Hard budgets: usage within W

TestHardBudgetUsageWithinW (bench v0.7.0, gateway v0.17.0, #87) sends requests through a gateway whose team has a budget. For each one, vLLM’s usage must stay within the worst case W the gateway held, W = prompts * max((L-M)*p_in + n*M*p_out, L*p_in), with L vLLM’s max_model_len (from its /v1/models) and M the max_tokens sent (the client’s, or the gateway’s, in X-Llmflow-Max-Tokens). It checks the tokens (prompt at most promptsL, completion at most promptsn*M) and the cost; that the ledger never passes the limit; and that a budget below the smallest W refuses with 429 before vLLM sees anything.

Run on 2026-10-28 with vLLM 0.32.1rc1 nightly CPU, Qwen2.5-0.5B-Instruct, --max-model-len 512 --max-num-seqs 2, and gateway v0.17.0 (the nightly needs --shm-size=1g, else it fails at start with “Insufficient space in /dev/shm”). Test prices 1000 / 5000 / 100 per million tokens (input / output / cached):

On a prompt near L, vLLM cut the output at L - input, as get_max_tokens says, which is why W counts L - M input tokens beside M output tokens.

The gateway repository also has TestPropertyNeverExceededPG, which needs a PostgreSQL: it runs three seeds of random traffic with replica kills (the run fails if fewer than 30 happened) and checks that no period’s cost passes the largest limit it ever had, and a planted control, the pre-#87 admission on the same workload, must exceed the limit, or the test fails because it could not see an overshoot. That is from the test’s source; this page did not run it.

Not measured: throughput or the latency the escrow adds to admission (the machine’s load was above the gate), and audio transcription.

HA mutual TLS between two replicas

TestHAMutualTLSLive (e2e/ha_mtls_test.go, bench v0.6.0) checks that two gateway replicas complete a mutual TLS 1.3 handshake on the HA internal port with certificate files (multi-line PEM): the path that gateway v0.16.0 broke and v0.16.1 fixed. It needs the gateway binary (BENCH_GATEWAY_BIN, v0.16.1 or later) and docker for a throw-away PostgreSQL (BENCH_PG_IMAGE, default postgres:18); no vLLM (the upstream is a fake). It skips, with the reason, when docker or the image is unavailable.

  1. A CA and two replica certificates (SAN llmflow-ha; ECDSA for A, Ed25519 for B) are generated and written as PEM files, keys at mode 0600; check-config accepts them.
  2. Replica A takes the pool’s lease; replica B starts.
  3. Requests go through B, the non-owner: all are 200 at priority 0, llmflow_ha_unowned_total stays 0, and with three requests held at the upstream the owner’s llmflow_inflight reads 3: the grants crossed the mTLS channel.
  4. Control. B restarts with a certificate another CA signed. It loads, but the owner does not answer: its requests are admitted without an owner (llmflow_ha_unowned_total 3, priority not 0). Without this, step 3 would prove nothing about the handshake.
go install github.com/go-llmflow/gateway/cmd/llmflow-gateway@v0.16.1
BENCH_GATEWAY_BIN=$(go env GOPATH)/bin/llmflow-gateway go test -v -run TestHAMutualTLSLive ./e2e

Run on 2026-10-27 with gateway v0.16.1 and PostgreSQL 18.6: it passes (8 of 8 admissions forwarded). With a v0.16.0 binary it fails at check-config (“holds more than one line”). The gateway repository has an in-process equivalent, TestHAMutualTLSProcesses, gated on LLMFLOW_TEST_PG_DSN. It is two processes on one machine, not a latency measurement.

Slurm discovery

Bench v0.5.0 tests the gateway’s Slurm discovery two ways.

A fake slurmrestd, without a cluster. The package fakeupstream provides Slurmrestd: GET /slurm/<version>/jobs/ answers the jobs given to SetJobs, in the shape of OPENAPI_JOB_INFO_RESP; job_state is a flag array (["RUNNING"], ["RUNNING","COMPLETING"]); a request must carry X-SLURM-USER-TOKEN set to Token; SetDown(true) simulates an outage (it answers 502).

e2e/slurm_test.go (TestSlurmDiscoveryE2E) runs on a real Slurm node, as root. It starts the gateway with a slurm model; submits, with sbatch --uid, a job of user alice in account physics that claims the model (it must never be trusted); submits a job of svc_llm named llmflow:llama:18100:3 and waits for the pool’s C to reach 3; sends a chat request through it; runs scancel, and checks that C falls back to 0 and the model is no longer served. It reads BENCH_SLURM_RESTD, BENCH_SLURM_API (default v0.0.42), BENCH_SLURM_JWT_FILE (the output of scontrol token username=svc_llm lifespan=7200), BENCH_SLURM_JOB, BENCH_SLURM_MODEL, BENCH_SLURM_MEM and BENCH_SLURM_WAIT.

Setup. One Debian trixie container with Slurm 24.11.5 (slurmctld, slurmd, slurmrestd, slurm-wlm-jwt-plugin, munge), AuthAltTypes=auth/jwt, slurmrestd run as an unprivileged user with data_parser versions v0.0.40 to v0.0.42, on arm64, with --privileged because slurmrestd needs to unshare namespaces. The job serves Qwen2.5-0.5B-Instruct on CPU and reads its key into VLLM_API_KEY, never through --api-key.

Job (2026-10-26, gateway #77 head, Slurm 24.11.5, data_parser v0.0.42)Result
fakevllmadmitted 2 s after sbatch, removed 2 s after scancel
vLLM CPU (--enforce-eager)admitted 18 s after sbatch (once /health and /v1/models answered), chat request 200, removed 2 s after scancel

Two earlier vLLM runs failed inside vLLM (too little /dev/shm; torch inductor found no C++ compiler). Each time the job stayed RUNNING with /health down, and the gateway correctly never admitted it. This is one small instance on one node, as the README says; it is no measure of a production cluster.

fakevllm 

fakevllm --addr 127.0.0.1:18000 --out requests.jsonl --model fake --reply "ok"

Flags: --addr, --out, --model, --reply, --delay, --token-delay, --max-body.

RouteAnswer
GET /v1/modelsone model, named by --model
POST /v1/messagesan Anthropic message; with "stream": true, the event sequence message_start, content_block_start, content_block_delta…, content_block_stop, message_delta (with usage.output_tokens), message_stop
any other POSTan OpenAI chat.completion; with "stream": true, chat.completion.chunk events (role, one chunk per word of --reply, finish), the usage chunk with empty choices when stream_options.include_usage is set, then data: [DONE]

Since v0.4.0 the /v1/messages route can mimic Anthropic’s behaviour:

FlagEffect
--status Nanswer every message with that status (429, 529, …)
--retry-after Sthe retry-after header sent with it, in seconds
--cache-read N, --cache-write-5m N, --cache-write-1h Nprompt-cache tokens reported in usage
--workspace ID (or per-key)the workspace named in the response headers
--ratelimit-headerssend the anthropic-ratelimit-* headers

Streams carry a ping event after message_start.

Usage is predictable: one prompt token per whitespace-separated word of the request’s message and system strings, and one completion token per word of --reply. --delay and --token-delay slow the answer and the stream.

Every request is appended to --out (mode 0600) as one JSON line, {"method","path","headers","body"}; a body that is not JSON is recorded as a string. The recording holds the headers as received, Authorization included. That is by design, since it is a witness of what a gateway forwarded. Use test keys only. If the record cannot be written, the request gets a 500, so a test never reads a silent gap as “nothing was forwarded”. Bodies are capped by --max-body (1 MiB; larger ones get a 413).
